# Repository guidance

## Workspace boundaries

- Use Node.js >=24.22 and root-pinned pnpm 11.25.0 (older 24.x on Windows randomly kills Vitest forks with native exit 0xC0000409, reported as "Worker exited unexpectedly"). Install from the root with `pnpm install --frozen-lockfile`; dependency edits update the single root lockfile. Root workspace settings enforce a 24-hour minimum release age and explicitly allow dependency build scripts.
- Workspace globs are `apps/*` and `packages/*`.
- The repository is Vue-only: there is no React/Next.js code. `apps/docs` is a VitePress site.
- Shared code lives in Just-in-Time packages that export source directly (no build step, no TypeScript `paths` used by their sources):
  - `@repo/ui` (`packages/ui`): shadcn-vue components (`@repo/ui/components/<name>`), `cn` (`@repo/ui/lib/utils`) and the shared Tailwind 4 setup (`@repo/ui/styles/theme.css`). Component sources import each other with relative paths and are excluded from ESLint to stay diffable against upstream.
  - `@repo/utils` (`packages/utils`): framework-agnostic functions (`cn`, `isExternalUrl`, `applyThemeClass`) and the shared ofetch-based `createApiClient`/`getErrorMessage`/`getErrorCode`, with Vitest tests.
  - `@repo/eslint-config` (Antfu-based `defineConfig`) and `@repo/typescript-config` (`base.json`) are used by admin, client, docs and the packages. Server keeps its own oxlint/Prettier/tsconfig.
- Versions shared by more than one workspace (vue, vue-router, vite, tailwindcss, reka-ui, typescript, vue-tsc, eslint, vitest, ...) live in the root `pnpm-workspace.yaml` `catalog:`; reference them as `catalog:` and add new shared versions there by hand.
- Read `apps/admin/AGENTS.md` or `apps/server/AGENTS.md` before changes there.

## Commands and verification

Run these from the repository root; directory targeting avoids guessing package names (`admin`, `client`, `server`, `docs`, `@repo/*`).

| Scope  | Development                         | Focused verification                                                                                                |
| ------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Admin  | `pnpm -C apps/admin dev` (5175)     | `pnpm -C apps/admin lint:fix`, `pnpm -C apps/admin build`, `pnpm -C apps/admin test`                                |
| Client | `pnpm -C apps/client dev` (5174)    | `pnpm -C apps/client lint:fix`, `pnpm -C apps/client build` (includes Vue typecheck), `pnpm -C apps/client test`    |
| Server | `pnpm -C apps/server dev` (3100)    | `pnpm -C apps/server lint`, `pnpm -C apps/server build`, `pnpm -C apps/server test`, `pnpm -C apps/server test:e2e` |
| Docs   | `pnpm -C apps/docs dev` (port 3001) | `pnpm -C apps/docs lint:fix`, `pnpm -C apps/docs check-types`, `pnpm -C apps/docs build`                            |
| UI     | —                                   | `pnpm -C packages/ui lint`, `pnpm -C packages/ui check-types`                                                       |
| Utils  | —                                   | `pnpm -C packages/utils lint:fix`, `pnpm -C packages/utils check-types`, `pnpm -C packages/utils test`              |

- Root `dev` starts all four apps; Vite/VitePress ports are strict. Root `lint` and `check-types` cover all apps and both packages; `test` and `test:coverage` cover admin/client/server/utils, `test:e2e` covers server. Typechecks and tests bypass Turbo cache; builds cache `dist/**` (docs builds into `apps/docs/dist`).
- All tests use Vitest from the root catalog. Each tested workspace has `test` (run once), `test:watch`, and `test:coverage`.
- Single tests: `pnpm -C apps/admin test src/utils/__tests__/env.test.ts`; `pnpm -C apps/client test src/composables/__tests__/useCollecty.test.ts`; `pnpm -C packages/utils test src/__tests__/theme.test.ts`; `pnpm -C apps/server exec vitest run src/modules/rbac/ability.spec.ts`. Admin/client/utils tests live in `src/**/__tests__/*.test.ts` and opt into DOM with `// @vitest-environment happy-dom`; client's happy-dom disables CSS file loading so tests stay offline. Server unit config matches `*.spec.ts`; e2e uses a separate config matching `test/**/*.e2e-spec.ts` and needs Docker (testcontainers).
- Admin requires `lint:fix` after code changes, build for non-trivial changes, and updated/run tests for core logic changes. Changes to `packages/ui` or `packages/utils` affect both admin and client: verify both apps. Template Git hooks are not auto-installed; run checks explicitly.
- Root `format` respects `.prettierignore`, which skips every workspace formatted by its own tooling. Use `lint:fix` (Antfu) for admin/client/docs/packages and server's local Prettier `format`.
- CI is `.github/workflows/ci.yml` (push to main, PRs): `pnpm lint`, `check-types`, `test`, `build`, a Drizzle check that fails when `apps/server/src/database/schema` changed without a generated migration, server `test:e2e`, and a build of the three Docker images. `release.yml` pushes the images to GHCR on `v*` tags (needs the repository variable `API_DOMAIN`). The workflows under `apps/admin/.github/` are template-local and never run.
- Production deployment lives in `deploy/` (single-host Docker Compose behind Caddy; read `deploy/README.md` first). Images build from the repository root with `apps/{server,admin,client}/Dockerfile`; keep their `ARG PNPM_VERSION` equal to `packageManager`, and add new files that must not reach images to the root `.dockerignore`. Admin/client images bake their `VITE_*` API URL at build time. Migrations must stay compatible with the previous release (expand/contract), because rollback means redeploying the previous image without a down migration. Dependency updates come from Renovate (`renovate.json`, waits 1 day to match `minimumReleaseAge`).

## Wiring and runtime gotchas

- Admin: `src/main.ts` registers `src/plugins/index.ts`; routing comes from `src/pages/**` plus generated layouts. Edit pages/layouts, not generated route tables. Vite generates `src/types/route-map.d.ts`, `auto-import.d.ts`, and `auto-import-components.d.ts`; do not hand-edit them. Client has no auto-import, so shared components must import every Vue API explicitly.
- Admin and client share the stack (Vue 3.5, Vue Router 5, Vite 8, Tailwind 4, reka-ui, `@lucide/vue`, TS 6). Admin uses file-based routes; client uses explicit routes in `apps/client/src/router/index.ts`.
- Theming: both apps import `@repo/ui/styles/theme.css` right after `tailwindcss` and define their own tokens (admin oklch, client hsl) on `:root`, `.dark` and `.theme-*` classes. Token values must be complete colors, not Tailwind 3 HSL triplets. `theme.css` makes Tailwind scan every shared component via `@source`.
- Client BuildY: `src/components/theming/themeManager.ts` persists `localStorage.currentState.sceleton` for the Tailwind 3 CDN page builder in `public/buildy`; keep the `hsl(var(--x))` config and the HSL triplets in `themes.ts` that it emits. `public/**` is not linted.
- Admin layouts use `vite-plugin-vue-layouts-next` (Vite 8 / Router 5 support), not the older plugin used by the upstream template. Client navigation icons are explicitly mapped in `MainNavigation.vue`; add route icons there instead of dynamically importing the entire icon library.
- New shadcn-vue components: run the CLI inside `packages/ui` (its `components.json` aliases point at `@repo/ui/*`), then rewrite generated `@repo/ui/...` imports to relative paths and add any new third-party dependency to `packages/ui/package.json`.
- Both apps' HTTP transport is `createApiClient` from `@repo/utils` (ofetch; cookies via `credentials: 'include'`, one shared `POST <authPath>/refresh` + retry on 401, `baseURL` is the app's versioned realm root, an app-specific `onUnauthorized` on refresh failure; errors are ofetch `FetchError`s whose `data` is the server's `{ statusCode, code, message, params?, details? }`; per-request `idempotencyKey: true | <key>` sends `Idempotency-Key` for server routes marked `@Idempotent()`, and `createIdempotencyKey()` makes one key per user operation that is reused on resubmits). Show errors through the app wrapper (admin `getErrorMessage` from `src/lib/api-client.ts`, client `errorMessage` from `src/lib/api.ts`): it translates `apiErrors.<code>` (with `params`; `NETWORK_ERROR`/`TIMEOUT` for requests without a response) and falls back to the server message for codes without a translation. Import `FetchError`/`isUnauthorized` from `@repo/utils`, the apps do not depend on `ofetch` directly. Client users and admin console accounts are separate server realms that never share accounts or cookies: the client uses `/v1/client/*` (`/v1/client/auth/*`, `/v1/client/users/me`, ...), the admin console `/v1/admin/*` (`/v1/admin/auth/*`, `/v1/admin/me`, ...; no sign-up, admins are created on its Admins page); only `/health` and `/avatars` are shared and unversioned. Admin's instance is `src/lib/api-client.ts` (`apiFetch` with `baseURL` `<API_BASE_URL>/v1/admin`, so service paths are relative like `/users`; sign-out on refresh failure); service/query functions live in `src/services/api/` (`auth`, `me`, `admin-users` for client users, `admins`, `roles`, `embedding-models`, `audit-logs`; the `example-*` modules and pages such as Tasks/Billing remain mock data). Env validation lives in `src/validators/env.validator.ts`, loaded by `src/utils/env.ts`; `.env.example` targets the server at `http://localhost:3100` + `/api`. The signed-in admin lives in `src/stores/auth.ts` (restored via `GET /v1/admin/me` by the router guard, not persisted); dashboard-layout pages require login and `meta.permission` gates pages, while `permission` on nav items hides sidebar/command entries. Admin two-factor authentication: when `POST /auth/login` answers `{ mfaRequired, challengeToken }`, `useAuth().login` keeps the challenge in the auth store (memory only, `pendingMfa`) and continues on `/auth/otp` (`MFA_PATH`), whose `verifyMfa` posts `/auth/login/mfa`; Settings → Security manages it via `/me/mfa` (QR codes rendered by `qrcode` in `src/lib/two-factor.ts`) and the Admins page resets it for others (`DELETE /admins/:id/mfa`).
- Client account pages (`src/pages/account/*`: login (offers `POST /auth/restore` when the account has a pending deletion), register with an emailed verification code via `POST /auth/register/send-code`, forgot/reset password, account with data export and account deletion cards in `src/components/account/`) use `src/lib/api.ts` (the shared client rooted at `<VITE_API_BASE_URL>/v1/client`; `onSessionExpired` handlers run on refresh failure) and the Pinia session store `src/stores/session.ts` (`useSessionStore`, not persisted, restored via `GET /v1/client/users/me` by the router guard; signing out drops the Vue Query cache). Pages run server calls through TanStack Vue Query `useMutation` (`isPending`/`error` instead of hand-written busy/failure refs); the shared `QueryClient` is `src/lib/query-client.ts` (no global error toast, 401s are not retried). `VITE_API_BASE_URL` defaults to `http://localhost:3100/api`. Both apps send their own reset page as `resetUrl` to their realm's `POST /auth/forgot-password`.
- Client i18n: `vue-i18n` (Composition API) is set up in `src/i18n/index.ts` with `en`/`zh` messages in `src/i18n/locales/*.ts`; `zh` is typed as `typeof en`, so a missing key fails `vue-tsc`. The locale comes from `localStorage.locale`, then the browser languages, then English; switch it with `setLocale()` (used by `LanguageSwitcher.vue` in the navbar). Components use `useI18n()`, non-component code imports `t` from `@/i18n`; route `meta.title`/`description` hold message keys. Tests pin English in `src/test-setup.ts`. Server errors are translated by `code` from the `apiErrors` messages.
- Admin i18n: `src/plugins/i18n/index.ts` creates the `vue-i18n` instance with `en.json`/`zh.json` (the schema is `typeof en`, so `zh.json` must have the same keys or `vue-tsc` fails) and exports `t` for non-component code plus `setLocale()`, which switches vue-i18n, dayjs and `<html lang>` together and stores the choice in `localStorage['app-locale']`. Nav `title`s in `src/constants/sidebar-data.ts` are message keys translated where rendered; zod messages use `error: () => t(...)` so they follow the current locale. The shell and the pages wired to the server are translated; mock example pages (Tasks, Billing, AI Talk, ...) and the Appearance/Notifications/Display settings tabs are still English. Components that call `$t` need the `i18n` plugin when mounted in tests.
- Server bootstrap is `src/main.ts` → `src/app.module.ts`, using Fastify and a global transforming/whitelisting validation pipe. Keep `.js` extensions on relative TypeScript imports (NodeNext ESM).
- Server needs its Docker stack (`pnpm -C apps/server infra:up`: PostgreSQL+pgvector, Redis, RustFS, Mailpit) plus `db:migrate`/`db:seed`; it loads `apps/server/.env` via `src/config/load-env.ts` and validates env with zod in `src/config/env.ts`. Web auth uses HttpOnly per-realm cookies; non-browser client apps (mini-programs, native apps) use the client realm with `X-Auth-Transport: bearer` + `Authorization: Bearer` (admin is cookie-only), data lives in Postgres via Drizzle, permissions use CASL. See `apps/server/AGENTS.md` for module conventions.
- Server e2e tests boot the real `AppModule` on Fastify through the shared `configureApp` against testcontainers, so they cover the production adapter stack.

# This is NOT the Turborepo you know

Turborepo configuration, task behavior, and CLI commands can vary between installed versions and may differ from your training data. Resolve the `turbo` package from this file's directory or relevant workspace; in monorepos, it may not be visible from the repository root. For example, run `node -p "require.resolve('turbo/package.json')"` from a workspace that depends on `turbo`.

Read `docs/README.md` inside that installed package first, then read the relevant pages from its `docs/` directory before changing Turborepo configuration or commands. Heed deprecation notices. These bundled docs match the installed package version and are available without network access.

This block is written and re-added by `turbo` before repository-scoped commands when an AI agent is detected. In the Turborepo source repository, its template is defined in `crates/turborepo-cli/src/cli/agent_guidance.rs`. Removing the managed block while updates are enabled means a later qualifying invocation will add it again. Set `"agentGuidance": true` in the root `turbo.json` or `turbo.jsonc` to opt in; this does not remove an existing block. Keep the block committed with your work to avoid an uncommitted change on the next agent invocation.
