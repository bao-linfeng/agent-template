# Server guidance (apps/server)

NestJS 12 + Fastify API that is meant to be built on, not a demo. Keep new code in the same shape so later agents can rely on these conventions.

## Workspace and commands

- Belongs to the root pnpm workspace: install from the repository root; dependency changes update the root `pnpm-lock.yaml` (no package-local lockfile). Run commands as `pnpm -C apps/server <script>`.
- Local infrastructure runs in Docker (`docker-compose.yml`): PostgreSQL 18 + pgvector, Redis 8, RustFS (S3) and Mailpit; `--profile ai` adds Ollama for local `bge-m3` embeddings, `--profile antivirus` clamd for the upload malware scan (`CLAMAV_HOST=localhost`), `--profile observability` the monitoring stack from `deploy/observability` (Grafana `http://localhost:3300`, Prometheus scraping the host API through `host.docker.internal:9464` via `prometheus.local.yml`, alert mail to Mailpit; see README "本地监控"). Compose reads `apps/server/.env` (`COMPOSE_PROFILES` there makes `infra:up` include profiles).
- First run: `cp .env.example .env` → `pnpm infra:up` → `pnpm db:migrate` → `pnpm db:seed` → `pnpm dev` (port 3100; it runs `docker compose up -d --wait` first and starts Nest with the tracing preload via `--exec`). The app fails to boot when Postgres or Redis is down. `.env.example` enables `COMPOSE_PROFILES=observability` and `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`, so dev includes the local monitoring stack and exports traces.
- Verify changes with `pnpm lint` (oxlint, type-aware), `pnpm check-types`, `pnpm build`, `pnpm test` (unit, `src/**/*.spec.ts`) and `pnpm test:e2e` (`test/**/*.e2e-spec.ts`, needs Docker; ~20 s container start). Format with `pnpm format` (local Prettier).
- Single unit spec: `pnpm exec vitest run src/modules/rbac/ability.spec.ts`. Single e2e file: `pnpm test:e2e test/rag.e2e-spec.ts`.
- Useful endpoints: Swagger UI `http://localhost:3100/api/docs` (JSON at `/api/docs-json`), Mailpit `http://localhost:8025`, RustFS console `http://localhost:9001`, readiness `GET /api/health`.

## Conventions

- NodeNext ESM: keep `.js` extensions on relative imports. Inject the DB with `@InjectDb() db: Database`, Redis with `@InjectRedis()`, config with `ConfigService<Env, true>` and `config.get('KEY', { infer: true })`. Never read `process.env` outside `config/` (exception: `tracing.ts` and `createFastifyAdapter`, which run before Nest config).
- New env var: add it to `config/env.ts` (with a default or a production rule) and to `.env.example`.
- Responses are plain JSON (no envelope); lists return `{ items, total, page, pageSize }` via `PaginationQueryDto`/`Paginated`. The global `ValidationPipe` uses `whitelist` + `forbidNonWhitelisted` + `transform`: unknown body fields are a 400.
- Errors: every error response is `{ statusCode, code, message, params?, details? }` (`ErrorBody`, Swagger `ErrorResponseDto`), written by the global `AllExceptionsFilter` (`common/errors`, registered in `setup-app.ts`). Throw `new AppException('<CODE>', { params })` with a code from `ERRORS` in `common/errors/error-codes.ts`; the catalog fixes status and English message, so add a code there instead of throwing Nest's built-in exceptions with free text. Codes are stable API that both web apps translate (`apiErrors.<CODE>` in their locales): never rename one, put interpolated values in `params` (also used by translations), and add translations to the app whose realm can return the code. Validation errors are `VALIDATION_FAILED` with `details: [{ field, constraints }]`; other `HttpException`s and Fastify errors get the generic code of their status; unknown errors become a logged 500 `INTERNAL_ERROR` without their message. Future streaming (SSE) events should reuse the same codes.
- DTOs: class-validator decorators in `dto/*.dto.ts`; the Swagger CLI plugin (`nest-cli.json`) derives OpenAPI schemas and uses JSDoc comments as descriptions, so do not add `@ApiProperty` unless the plugin cannot infer the type. Do not spread DTO instances into inserts (oxlint `no-misused-spread`); pick fields explicitly.
- Database changes: edit `src/database/schema/*.ts` → `pnpm db:generate --name <change>` → review the SQL → `pnpm db:migrate`. Hand-written SQL (extensions, partial/expression indexes, CHECKs) goes into `pnpm exec drizzle-kit generate --custom --name <change>`. Columns use `casing: 'snake_case'`; tables get `...timestamps`. Map pg errors with `isUniqueViolation` / `isForeignKeyViolation` (covers 23503 and RESTRICT's 23001).
- Pool limits (`createPool` in `database/database.ts`): every app connection runs with `statement_timeout` (`DATABASE_STATEMENT_TIMEOUT_MS`, 30 s, error 57014), `idle_in_transaction_session_timeout` (`DATABASE_IDLE_IN_TRANSACTION_TIMEOUT_MS`, 60 s; the server ends the session) and a 5 s wait for a connection (`DATABASE_CONNECTION_TIMEOUT_MS`). Never await external calls (HTTP, embeddings, storage) inside `db.transaction`; do them before or after. Work that legitimately runs longer either goes in batches (`deleteInBatches`) or uses a dedicated `pool.connect()` client with `SET statement_timeout = 0` released with `release(true)` (see `ensureVectorIndex`). Migrations run without the statement limit. Connection errors outside a query are logged by the pool's listeners; do not remove them, an unhandled `error` event crashes the process.
- Background work: register a queue name in `infra/queue/queue.module.ts` `QUEUES`, `BullModule.registerQueue` in the feature module, and a `@Processor` extending `WorkerHost`. Throw `UnrecoverableError` for permanent failures. Workers run inside the API process. Recurring work uses a BullMQ job scheduler (`queue.upsertJobScheduler(id, { pattern })` in `onApplicationBootstrap`; `removeJobScheduler` when an env switch disables it, while tasks behind a runtime setting stay scheduled and return early when it is off), which runs each tick once per cluster; do not add `@nestjs/schedule` `@Cron`, which would run on every instance. Housekeeping that spans modules goes into `modules/maintenance` (a provider with `run(before)` plus a case in `MaintenanceProcessor`); delete rows with `deleteInBatches` (`database/batch-delete.ts`) to keep locks short.
- Files: use `StorageService` (`putObject`, `getObject`, `deleteObject`/`deleteObjects`, `deletePrefix`, `listObjects`, `getPresignedUrl`). Keys are server-generated (`avatars/<accountId>/<uuid>.<ext>` for both realms, `rag/<kbId>/<docId>/source.<ext>`, `exports/<userId>/<exportId>.json`), never raw user input. Write the object before the row that references it: the nightly orphan sweep (runtime setting `maintenance.storageOrphanSweepEnabled`, 04:00) deletes objects under `avatars/`, `rag/` and `exports/` older than 24 h whose row is gone or points elsewhere, and leaves keys of unknown shape alone. A new key family needs a pattern in `parseObjectKey` and a reference check in `OrphanObjectsCleanup`, or it is never swept. Read uploads with `readSingleFile(request, maxBytes)` (field `file`), validate the type from the content (never the client MIME type or name alone; see `detectImageType`), then call `AntivirusService.assertClean(buffer)` before storing anything. It scans with clamd when `CLAMAV_HOST` is set (no-op otherwise) and fails closed: 422 `UPLOAD_INFECTED`, 503 `UPLOAD_SCAN_UNAVAILABLE` when clamd is unreachable, slow (`CLAMAV_TIMEOUT_MS`) or errors. Upload large generated files from disk with `putFile(key, path, contentType)` instead of buffering them.
- Mail: add a template function to `infra/mail/mail.templates.ts`, then `MailService.send(to, template(...))`. Never send synchronously. Mail that tells an account about something that happened (not codes, reset links or mail to accounts that cannot sign in) goes through `NotificationsService.notify` instead (see "Notifications and announcements"), which also stores it in-app and respects preferences.
- Secrets at rest (provider API keys, TOTP secrets): inject `SecretBox` (global `CryptoModule`), store `encrypt()` output in a `text` column named `*Encrypted`, decrypt only where the value is used and never return it. `SecretBox` encrypts with `ENCRYPTION_KEY` and also decrypts with `ENCRYPTION_KEYS_PREVIOUS`, keeping the `v1.` format so the previous release can still read new values. Every new encrypted column must be added to `ENCRYPTED_COLUMNS` in `database/reencrypt-secrets.ts`, or key rotation leaves its values on the old key; values kept only in Redis must expire (rotation waits for their TTL).

## Runtime settings and feature flags

- Env (`config/env.ts`) is read once at boot. Settings administrators change while the API runs live in `modules/settings`: `SETTINGS` in `settings.catalog.ts` declares each key (`<area>.<name>`, e.g. `auth.registrationEnabled`) with a bounded zod schema, its default (usually the env variable it replaces, which stays as that default), a `public` flag and a description; table `system_settings` stores only overrides (`key`, `value` jsonb, `updated_by`). Current keys: `auth.registrationEnabled` (public), `account.deletionGraceDays`, `maintenance.authRecordRetentionDays`, `maintenance.storageOrphanSweepEnabled`, `notifications.retentionDays`, and the env-bound limits `rateLimit.defaultLimit`/`rateLimit.authLimit` (≤ `THROTTLE_LIMIT`/`AUTH_THROTTLE_LIMIT`), `session.adminTtlSeconds`/`session.clientIdleTtlSeconds` (≤ `REFRESH_TOKEN_TTL_SECONDS`), `session.clientMaxTtlSeconds` (≤ `CLIENT_SESSION_MAX_TTL_SECONDS`), `auth.passwordResetTtlSeconds` (≤ `PASSWORD_RESET_TTL_SECONDS`), `auth.emailCodeTtlSeconds` (≤ `EMAIL_CODE_TTL_SECONDS`), `auth.emailCodeResendSeconds` (≥ `EMAIL_CODE_RESEND_SECONDS`), `auth.emailCodeMaxAttempts` (≤ `VERIFICATION_CODE_MAX_ATTEMPTS` = 5).
- Read with `SettingsService.get(key)` (global module, synchronous, typed) at the moment the value is used; never copy it into a field in a constructor, or changes need a restart. Every instance keeps the overrides in memory, reloads after a change through Redis pub/sub (`settings:changed`) and every 60 s as a fallback, so reads cost nothing on hot paths and other instances follow within moments.
- `GET /v1/admin/settings` (`setting:read`) lists every key with `value`, `defaultValue`, `overridden`, JSON Schema (`schema`, for forms) and `updatedAt`/`updatedBy`; `PATCH /v1/admin/settings` (`setting:manage`, `{ values: { <key>: <value> | null } }`, `null` restores the default) applies all changes in one transaction or none (400 `SETTING_UNKNOWN` / `SETTING_INVALID` with `params.key`) and is audited like every write. `GET /v1/client/settings` (public, no session) returns the `public` keys for UI decisions such as hiding sign-up.
- Keep infrastructure, secrets, values needed before Nest boots and switches that weaken security or hide tracks (`AUDIT_LOG_ENABLED`, `AUDIT_LOG_READS`, `COOKIE_*`, `CORS_ORIGINS`, ...) env-only. A runtime setting may only narrow what env allows: give it a schema function of the env (`schema: (env) => upTo(env('X'), min)`), so the env value is the hard limit shown to and enforced on administrators, and stored values beyond a later-lowered env limit are ignored. Throttle windows (`*_TTL_SECONDS`) and `ACCESS_TOKEN_TTL_SECONDS` stay env-only (revocation markers live as long as access tokens, so shortening it at runtime would let earlier tokens outlive them).
- New setting: add it to `SETTINGS`, read it via `get()`, list it here, and add its title/description to the admin console i18n (`systemSettings.items.<key>` in `apps/admin/src/plugins/i18n/{en,zh}.json`; the System Settings page builds the control from the JSON Schema and falls back to the key and `description` without them). Keys and schemas are stable API: the previous release must still read every stored value it knows (rows of unknown keys and values that fail the schema are ignored with a warning, falling back to the default), so rename a key by adding a new one.

## Notifications and announcements

- `modules/notifications` (global module). Personal notifications live per realm in `user_notifications` / `admin_notifications` (`uuidv7` ids, `type` + `params` jsonb + optional `link`, `read_at`; cascade with the account). Rows store the type code, never rendered text: the API returns `type`, `category`, `params` and an English `title`/`body` rendered from the catalog, and the web apps translate `notifications.types.<type>.{title,body}` with `params` (like `apiErrors.<code>`).
- `notifications.catalog.ts`: `NOTIFICATION_CATEGORIES` (`security` is mandatory, `account`, `knowledgeBase`) and `NOTIFICATION_TYPES` (category, realms, channels `inApp`/`email`, zod `params`, English `title`/`body` with `{param}` placeholders, per-realm default `link` as an app route). Types and categories are stable API: add new keys instead of renaming them or changing params incompatibly, and translate new types in the app(s) of their realms. Current types: `security.passwordChanged` (both realms), `security.twoFactorChanged` (admin), `account.deletionCancelled`, `account.exportReady`, `knowledgeBase.documentReady`, `knowledgeBase.documentFailed` (in-app only). Account deletion scheduled/purged mail, verification codes and reset links stay plain `MailService.send`.
- Send with `NotificationsService.notify({ realm, recipientId, type, params, link?, mail? })` after the change has been committed. It is typed by `type`: `realm` must be one of the type's realms and `mail` (`{ to, ...mailTemplates.x(...) }`) is required exactly when the type has the `email` channel. It skips channels the recipient switched off (mandatory categories always deliver), inserts the row, signals the recipient's streams and queues the mail; a recipient deleted meanwhile is skipped, invalid params throw (programming error). Workers that notify catch and log notification failures so they neither retry the work nor hide its error (`IngestProcessor.notifyOwner`).
- Inbox routes (no permission, own data; one base controller `NotificationInboxController` for `/v1/client/notifications` and `/v1/admin/notifications`): `GET /` (`page`, `pageSize`, `unread=true|false`, `category`), `GET /unread-count` (`{ notifications, announcements, total }`), `POST /:id/read` (204, 404 `NOTIFICATION_NOT_FOUND` for other accounts), `POST /read-all` (`{ updated }`), `DELETE /:id`, `GET`/`PATCH /preferences` (`{ preferences: { <category>: { <channel>: boolean } } }`, atomic, channels merge; 400 `NOTIFICATION_CATEGORY_UNKNOWN` / `NOTIFICATION_CATEGORY_MANDATORY` / `NOTIFICATION_PREFERENCE_INVALID`), `GET /announcements`, `POST /announcements/:id/read`, `POST /announcements/read-all`, `GET /stream`. Read-marking routes are audited only on failure (`@Audit({ mode: 'failures' })`). Preferences live in `*_notification_preferences` (`account_id` + `category` → `channels` jsonb, missing = on).
- Announcements (`announcements`, `announcement:read` / `announcement:manage`, not granted to system roles): `/v1/admin/announcements` list (`status` = `draft|published|expired`, `audience`, `keyword` on the title) with `readCount`, create (draft or `publish: true`), `PATCH`, `POST /:id/publish` (no-op when published), `POST /:id/withdraw` (back to draft), `DELETE`. `audience` is `user`, `admin` or `all`, `level` `info|warning|critical`, `body` plain text (clients must not render it as HTML), optional `expiresAt` (must be in the future: 400 `ANNOUNCEMENT_EXPIRY_INVALID`). Stored once and matched by audience when read; read marks are rows in `*_announcement_reads` (written only on read, no fan-out). No scheduled publishing yet.
- Event stream `GET .../notifications/stream` (`text/event-stream`, cookie or bearer): `retry: 5000`, then `ready`, `notification` (full view), `announcement` (`{ id }`), `sync` (`{ reason: read|deleted|preferences }`), `: ping` every 25 s. Events are signals: clients refetch on `ready` and on every event. `NotificationStreamService` publishes on Redis (`notifications:<realm>:<accountId>`, `notifications:broadcast:<realm>`) and keeps one subscriber connection per instance, so events cross instances. A stream is authenticated once: it ends after `ACCESS_TOKEN_TTL_SECONDS` and at the next 25 s sweep after its session was revoked (the client then reconnects and refreshes or is signed out); at most 5 per account and instance (the oldest is closed), slow readers (64 KiB buffered) are dropped, and all streams end in `onModuleDestroy` so shutdown does not wait for them. The route is excluded from the HTTP duration metric and from tracing (long-lived). Browsers cannot send `Authorization` with `EventSource`, and its reconnects skip the 401 refresh: read the stream with `fetch` through the app's API client (both web apps use `connectEventStream` from `@repo/utils` with `responseType: 'stream'`). nginx-like proxies honour the `X-Accel-Buffering: no` the route sends; Caddy flushes event streams by itself.
- Retention: `NotificationsCleanup` (`maintenance` job `notifications-prune`, 03:20, always scheduled) deletes personal notifications older than `notifications.retentionDays` (runtime setting, default 90, 0 = keep); announcements stay until deleted.

## Concurrency and duplicate submissions

- Distributed locks: inject `RedisLockService` (global, from `RedisModule`) instead of writing ad-hoc `SET NX` code. `withLock(key, (signal) => task, { ttlMs?, waitMs?, retryDelayMs? })` holds `lock:<key>` while the task runs, renews the lease every `ttlMs / 3` (default lease 30 s, which only bounds how long a crashed holder blocks others), always releases it and answers 409 `RESOURCE_LOCKED` when the lock stays busy for `waitMs` (default 0 = fail fast). `signal` aborts if the lease is lost; long tasks (LLM streams) should stop on it. `acquire`/`tryAcquire` return a `Lock` with token-checked `extend`/`release` for manual control. Name keys `<domain>:<purpose>:<id>`: `rag:ingest:<documentId>` serializes ingest jobs of one document; a conversation module should run each reply under `chat:conversation:<id>` (fail fast → the client sees 409 while a reply is still being generated). Locks are leases, not fencing: invariants that must never break still need a DB constraint or transaction.
- Idempotency keys: decorate retry-prone write routes with `@Idempotent({ required?, ttlSeconds? })` (`common/idempotency`); the global `IdempotencyInterceptor` ignores other routes. Clients send `Idempotency-Key: <uuid>` (1-255 printable ASCII, optionally quoted); it is scoped per account (`<realm>:<id>`, `ip:<ip>` on public routes) and fingerprinted by method + URL + parsed JSON body (key order ignored; multipart bodies are not included). Outcomes: first request runs; retries within `ttlSeconds` (default 24 h) get the stored JSON body with `Idempotent-Replayed: true` (exposed via CORS); a duplicate while the first is running is 409 `IDEMPOTENCY_KEY_IN_PROGRESS`; the same key for a different request is 422 `IDEMPOTENCY_KEY_MISMATCH`; a malformed header is 400 `IDEMPOTENCY_KEY_INVALID`, a missing one with `required: true` 400 `IDEMPOTENCY_KEY_REQUIRED`. Failed requests (including validation errors) are forgotten, so the same key can be retried. Only the body is replayed (status comes from the route), so do not use it on routes that set cookies/headers (auth). Used on the client RAG create routes (knowledge base, upload, text document). Web apps send the header through `createApiClient` (`@repo/utils`): `idempotencyKey: true` per call, or one `createIdempotencyKey()` per form/operation passed on every attempt so double clicks and manual retries collapse into one run.

## Audit log

- Every request that reaches a Nest route is audited into `audit_logs` without extra code: writes (POST/PUT/PATCH/DELETE) always, GET/HEAD only with `AUDIT_LOG_READS=true`; requests rejected by guards (401/403/429) and failed ones are included with their error `code`. `AuditGuard` (first global guard, never blocks) attaches `request.audit`, `AuditInterceptor` remembers the returned `id` as `resourceId` (otherwise route `:id`), `AllExceptionsFilter` sets `errorCode`, and the `onResponse` hook from `registerAuditHook` (`setup-app.ts`) hands the row to `AuditService`, which inserts in batches after the response and flushes on shutdown. Unknown paths and body-parse errors never reach a route and are not audited.
- Rows store realm, actor id/email (copied, no FK), action (`<Controller>.<handler>`), method, route pattern, path, params, sanitized query/body, status, duration, IP, user agent and `x-request-id`. Bodies are sanitized by `sanitize()` in `audit-context.ts`: keys matching password/secret/token/api key/authorization/cookie become `[redacted]` (null/empty stay visible), long strings/arrays are truncated, multipart bodies are not stored. Never log secrets under other key names: add them with `@Audit({ redact: ['field'] })`.
- Tune routes with `@Audit({ action?, mode?, redact? })` (`mode`: `always` also records reads, `failures` only >= 400 as on `auth/refresh`, `never`). Public sign-in routes call `setAuditActor(request, account)` so successful logins/registrations have an actor; failed ones keep the submitted email.
- The account purge (see "Account deletion and data export") is the only writer that updates rows: it clears `actor_email` and `body` of rows about a purged client user and keeps the rest.
- Admins read it via `GET /v1/admin/audit-logs` (filters: `realm`, `actorId`, `action`, `method`, `resourceId`, `outcome`, `from`/`to`, `keyword`) with `audit-log:read`. `AUDIT_LOG_RETENTION_DAYS` (default 180, 0 = forever) is enforced by a BullMQ job scheduler on queue `audit` at 03:00. `AUDIT_LOG_ENABLED=false` turns collection off. `id` is `uuidv7()` (PostgreSQL 18), so lists sort by `createdAt, id`.

## Auth and permissions

- Two account realms that share nothing (`modules/auth/realms.ts`): **client users** (`users`, `auth_sessions`, `password_reset_tokens`; self-registered, no roles) and **admin console accounts** (`admin_users`, `admin_sessions`, `admin_password_reset_tokens`, `admin_user_roles`; created by administrators via `/v1/admin/admins` or the seed, no registration). The same email may exist in both as unrelated accounts. Both table sets come from the same column factories, so realm-aware services (`SessionsService`, `AccountsService`, `AuthService`) take a `realm` argument and pick tables from `REALM_TABLES`.
- Realm controllers are grouped by folder: `@ClientController` classes go in `<module>/client/`, `@AdminController` classes in `<module>/admin/` (e.g. `rag/client/knowledge-bases.controller.ts`, `rag/admin/knowledge-bases.controller.ts`); services, DTOs, workers and realm-agnostic bases (`CredentialsController`, `AccountMeController`) and public `@Controller`s stay at the module root. A new realm gets its own folder name in every module it touches.
- Routes are split by realm and URI-versioned (`enableVersioning` in `setup-app.ts`): `@ClientController('<path>')` mounts at `/<prefix>/v1/client/<path>` and only accepts client sessions, `@AdminController('<path>')` at `/<prefix>/v1/admin/<path>` and only accepts admin sessions. Plain `@Controller` is only for realm-less `@Public()` routes (`/health`, `/avatars`, unversioned); `JwtAuthGuard` throws on a protected route without a realm. Never hand-write `client/`, `admin/` or `v1/` into a plain `@Controller` path. Every route requires authentication unless decorated `@Public()`. Credential endpoints add `@AuthThrottle()` (stricter per-IP limit: window `AUTH_THROTTLE_TTL_SECONDS`, count runtime setting `rateLimit.authLimit`; the default limit (`THROTTLE_TTL_SECONDS`, `rateLimit.defaultLimit`) applies everywhere, counters in Redis).
- Cookies (HttpOnly, per realm so both sessions coexist in one browser): client `access_token` (path `/api/v1/client`) + `refresh_token` (path `/api/v1/client/auth`); admin `admin_access_token` (path `/api/v1/admin`) + `admin_refresh_token` (path `/api/v1/admin/auth`). Paths derive from `REALM_COOKIES`, so a new API version moves the cookies with it. The JWT carries `realm`, and a token presented to the other realm is rejected. Clients (`apps/admin/src/lib/api-client.ts` with `baseURL` `<api>/v1/admin`, `apps/client/src/lib/api.ts` with `<api>/v1/client`) call `POST /auth/refresh` relative to that root on 401 and retry once, so only use 401 for a missing/expired session (e.g. a wrong current password is 400). `forgot-password` accepts `resetUrl` limited to `APP_WEB_URL`/`CORS_ORIGINS` origins. Client registration needs an emailed code (both steps answer 403 `AUTH_REGISTRATION_DISABLED` while the runtime setting `auth.registrationEnabled` is off): `POST /auth/register/send-code` (`{ email }` → 202 `{ expiresIn, resendAfter }`; 409 if registered, 429 within `auth.emailCodeResendSeconds`), then `register` with `code`. Codes come from `VerificationCodesService` (Redis only, hashed, lifetime `auth.emailCodeTtlSeconds`, single use, scoped by realm/purpose/email, discarded after `auth.emailCodeMaxAttempts` wrong guesses); reuse it with a new `VerificationPurpose` for other email proofs. CORS methods are listed explicitly in `setup-app.ts` (`@fastify/cors` defaults to GET/HEAD/POST); refresh tokens rotate, and replaying a rotated token outside a 30 s grace window revokes the session. Client sessions slide (`SLIDING_SESSION_REALMS`): every refresh extends them by `session.clientIdleTtlSeconds`, capped at `session.clientMaxTtlSeconds` (default 30 days) after sign-in; admin sessions end `session.adminTtlSeconds` after sign-in (runtime settings bounded by the env TTLs; changes apply to new sign-ins and the next refresh). The refresh cookie `maxAge` and bearer `refreshExpiresIn` follow the session's remaining lifetime. Logout, password change/reset, disabling an account and requesting its deletion revoke sessions and mark them in Redis, so access tokens die immediately. Sessions that expired or were revoked, and reset tokens that expired or were used, are deleted `maintenance.authRecordRetentionDays` (runtime setting, default `AUTH_RECORD_RETENTION_DAYS` = 30, 0 = keep forever) later by the `maintenance` job at 03:30.
- Bearer transport (realms in `BEARER_REALMS`, i.e. client users only; for mini-programs and native apps that cannot keep HttpOnly cookies): send `X-Auth-Transport: bearer` to `login`/`register`/`refresh`/`logout`. Sign-in then returns `{ account, tokens }` (`tokens`: `tokenType`, `accessToken`, `expiresIn`, `refreshToken`, `refreshExpiresIn`) and sets no cookies; `refresh` takes `{ refreshToken }` in the body and answers 200 with new `tokens` (it still rotates); `logout` uses `Authorization` and/or the body `refreshToken`. API calls send `Authorization: Bearer <accessToken>`, which `JwtAuthGuard` prefers over the cookie. Unknown `X-Auth-Transport` values, `bearer` on the admin realm and a body `refreshToken` without the header are 400s; admin routes ignore `Authorization`. Helpers live in `modules/auth/bearer.ts`.
- Two-factor authentication (admin realm only, optional per admin; `modules/mfa`): an authenticator app (TOTP, RFC 6238 in `totp.ts` without dependencies, SHA-1/6 digits/30 s, ±1 step) plus 10 one-time recovery codes (`xxxxx-xxxxx`, case/space/dash-insensitive). Tables `admin_totp_credentials` (secret encrypted with `SecretBox`, `last_used_step` so each code works once) and `admin_recovery_codes` (sha256 hashes). Self-service under `/v1/admin/me/mfa`: `GET` status, `POST totp/setup` (`{ password }` → `{ secret, otpauthUri, expiresIn }`, pending secret in Redis for 10 min), `POST totp/enable` (`{ code }` → `{ recoveryCodes }`, signs out other sessions), `POST totp/disable` and `POST recovery-codes` (`{ password, code }`; `code` is a 6-digit TOTP or a recovery code everywhere). With TOTP on, `POST /v1/admin/auth/login` answers 200 `{ mfaRequired: true, challengeToken, expiresIn }` without cookies; `POST /v1/admin/auth/login/mfa` (`{ challengeToken, code }`) sets them. Challenges live in Redis (hashed, 5 min, `MFA_CHALLENGE_MAX_ATTEMPTS` = 5 counted atomically before the check, single use); failures are 400 (`AUTH_MFA_CODE_INVALID`, `AUTH_MFA_CHALLENGE_INVALID`), never 401. `DELETE /v1/admin/admins/:id/mfa` (`admin:update`, not on yourself) resets it for an admin who lost the device and revokes their sessions; password reset never removes the second factor. Enable/disable/reset email the admin; `code` is redacted from audit bodies. `MFA_TOTP_ISSUER` names the account in authenticator apps. Other realms opt in by overriding `CredentialsController.secondFactor`.
- RBAC exists only for admin accounts. Permissions are codes `<subject>:<action>` in `modules/rbac/permissions.ts` (`PERMISSIONS`, `SYSTEM_ROLES`). Roles store code arrays; `super_admin` is forced to `all:manage` on boot. Per-admin permissions are cached in Redis — call `RbacService.invalidateAdmin(id)` after changing an admin's roles and `invalidateAll()` after changing role permissions.
- Admin routes: `@RequirePermissions('user:read')` (requires an unconditional rule, i.e. access to _all_ records); `@CurrentAbility()` gives the CASL ability for record-level checks (`assertCan(ability, action, asSubject(type, row))`, conditions defined in `defineAbilityFor`). Client sessions have no ability: policies on client routes always deny.
- Client routes authorize by ownership in the service (e.g. `KnowledgeBasesService.getOwned(id, user.id)`, which answers 404 for other users' rows). `@CurrentUser()` returns `{ id, email, sessionId, realm }`.
- To protect a new admin resource: add its subject to `SUBJECTS` and codes to `PERMISSIONS`, then use the decorators above on an `@AdminController`. Grant it to system roles only if every deployment needs it.

## Account deletion and data export

- Retention policy for client users: deletion is a soft delete with a grace period, then a hard purge. Admin console accounts are disabled, not deleted (the columns exist on `admin_users` because both tables share one factory, but nothing sets them there).
- `POST /v1/client/users/me/deletion` (`{ password }`, 202 `{ deletionScheduledAt }`) or `POST /v1/admin/users/:id/deletion` (`user:delete`, not granted to system roles) sets `users.deletion_requested_at` and `deletion_scheduled_at` (runtime setting `account.deletionGraceDays`, default `ACCOUNT_DELETION_GRACE_DAYS` = 15; a change only affects later requests), revokes every session and emails the user; repeating keeps the first schedule. The email stays taken during the grace period. `login` answers 403 `AUTH_ACCOUNT_PENDING_DELETION` with `params.scheduledAt`, but only after the password matched; `refresh` rejects such accounts. `POST /v1/client/auth/restore` (login body and response, cookie or bearer) cancels the deletion and signs in; `DELETE /v1/admin/users/:id/deletion` cancels it for the user. Password reset keeps working so owners can still restore. Once `deletion_scheduled_at` has passed the deletion is final (409 `ACCOUNT_DELETION_NOT_CANCELLABLE`), which lets the purge work in steps without racing a restore.
- `DeletedAccountsCleanup` (`maintenance` job `account-purge`, 03:45, always scheduled) purges due accounts in batches: RAG chunks first via `deleteInBatches`, then the `users` rows (cascading to sessions, reset tokens, knowledge bases, documents, exports) in one transaction with the audit scrub, then `avatars/<id>/`, `exports/<id>/` and `rag/<kbId>/` objects (best effort, the orphan sweep catches the rest) and a goodbye email. New tables holding client user data must reference `users` with `onDelete: 'cascade'` (or `set null`), and new storage key families of a user need a prefix in `deleteFiles`, or the purge leaves personal data behind.
- Data export: `POST /v1/client/users/me/exports` (202, `@Idempotent`, one pending/processing export per user via a partial unique index, else 409 `ACCOUNT_EXPORT_IN_PROGRESS`) queues `account-export`; `AccountExportProcessor` streams one JSON file (`AccountExportBuilder`: profile, avatar as base64, sessions, knowledge bases, documents with their source text, notifications with preferences and read announcements, own audit trail; no password hashes or embeddings; format `agent-template/account-export` v1) through a temp file to `exports/<userId>/<exportId>.json` and emails the user. `GET .../exports`, `GET .../exports/:id`, `GET .../exports/:id/download` (409 `ACCOUNT_EXPORT_NOT_READY`, 410 `ACCOUNT_EXPORT_EXPIRED` after `ACCOUNT_EXPORT_TTL_HOURS`, default 72). `AccountExportsCleanup` (`account-exports-prune`, 03:15, always scheduled) deletes expired exports and ones stuck unfinished for 24 h. Add new personal data to the builder and bump `version` when renaming or removing fields.

## Embeddings and RAG

- Embedding models live in `ai_embedding_models` and are managed through `/api/v1/admin/ai/embedding-models` (permission `embedding-model:*`). Provider type `openai_compatible` calls `POST {baseUrl}/embeddings` (OpenAI, Ollama `/v1`, vLLM, Xinference, TEI, SiliconFlow...). API keys are AES-256-GCM encrypted with `ENCRYPTION_KEY` and never returned (`hasApiKey` only). Exactly one default model (seeded: `bge-m3`, 1024 dims, Ollama URL).
- `rag_chunks.embedding` is an untyped `vector`; each row stores `dimensions` (CHECK keeps them equal) and every dimension has a partial HNSW index `rag_chunks_embedding_<n>_hnsw` on `(embedding::vector(n)) WHERE dimensions = n`. `EmbeddingModelsService.ensureVectorIndex` creates it (CONCURRENTLY) when a model with a new dimension is saved; 1024 is created by migration 0002. Queries must use the same cast and a literal dimension (see `RetrievalService`) or the index is skipped. Max 2000 dims.
- A knowledge base is bound to one embedding model forever; `model`/`dimensions` of a model in use cannot change — create a new model and re-ingest instead.
- Ingestion: upload/text → object stored → `rag-ingest` job → `parseDocument` (UTF-8 text formats only: txt, md, csv, json, html; add PDF/DOCX parsers in `document-parsers.ts`) → `splitText` (recursive, CJK aware) → embed in `batchSize` batches → chunks replaced in one transaction. Document status: `pending → processing → ready | failed`.
- Knowledge bases belong to client users (`ownerId` → `users`). Administrators list/inspect/delete every knowledge base via `/v1/admin/rag/knowledge-bases` (`knowledge-base:read` / `knowledge-base:manage`).
- From code (agents, tools), call `RetrievalService.retrieve(kb, query, { topK, minScore })` after loading the knowledge base with `KnowledgeBasesService.getOwned(id, userId)` (or `get(id)` on admin paths).

## Observability

- Prometheus metrics live in `infra/metrics` (`MetricsModule`, global). `MetricsService` owns the `prom-client` registry and serves it on its own listener `METRICS_HOST:METRICS_PORT` (default `0.0.0.0:9464`, `GET /metrics` only); the API port never serves it and the gateway only proxies `PORT`, so do not add a `/metrics` route or publish the port. `METRICS_ENABLED=false` turns everything off; e2e uses `METRICS_PORT=0` (read the bound port with `MetricsService.address()`).
- Recorded without extra code: `http_server_request_duration_seconds{method,route,status_code,realm}` from the `onResponse` hook `registerMetricsHook` (`setup-app.ts`; `route` is the Fastify route pattern, `unmatched` without one, `/health` and `notifications/stream` skipped), BullMQ metrics from `QueueMetrics` (`bullmq_queue_jobs{queue,state}` for every name in `QUEUES`, read on scrape and cached 10 s, the same cluster-wide value on every instance; `bullmq_jobs_processed_total`, `bullmq_jobs_failed_final_total` (no retry left or `UnrecoverableError`), `bullmq_job_duration_seconds` and `bullmq_job_last_success_timestamp_seconds` per `queue`/job `name` for every `@Processor` found through discovery), pg pool gauges (`PoolMetrics`), `upload_scans_total{result}` (`AntivirusService`), `notification_streams_open{realm}` (`NotificationStreamService`, per instance) and the `prom-client` default Node metrics.
- New metrics: inject `MetricsService` and create the metric with `registers: [metrics.registry]` once (constructor or `onModuleInit`), only when `metrics.enabled`. Labels must have a small fixed set of values: never put ids, emails, raw paths or error messages into labels. Job names are labels too, so keep them constant (`'send'`, `'ingest'`, scheduler ids), not per-record.
- Tracing (OpenTelemetry, viewed in Tempo/Grafana) is started by the preload `src/tracing.ts` before the app imports anything, because the instrumentations must patch pg/ioredis/pino first and ESM imports need the `import-in-the-middle` loader it registers; `pnpm dev` loads it through `nest start --exec "node --import ./dist/tracing.js"`; `nest start`, `start:debug` and the tests run without it. It is on when `OTEL_EXPORTER_OTLP_ENDPOINT` (or `..._TRACES_ENDPOINT`) is set and `OTEL_SDK_DISABLED` is not, exported over OTLP (`OTEL_EXPORTER_OTLP_*`), traces only. `infra/tracing/sdk.ts` instruments incoming/outgoing HTTP, `fetch` (undici), pg and ioredis (only inside a request or job: `requireParentSpan`), and adds `trace_id`/`span_id` to pino logs; BullMQ gets `bullmq-otel` through `telemetry` in `QueueModule` when `TRACING_ENABLED`, so a job continues the trace of the request that queued it. `TracingSampler` samples `OTEL_TRACES_SAMPLER_ARG` of new traces (parent-based; `OTEL_TRACES_SAMPLER` is ignored) and never starts traces for BullMQ polling/stalled checks. `/health`, `/metrics` and notification streams are not traced. `registerTracingHook` (`setup-app.ts`) names the request span `<METHOD> <route pattern>` and returns a `traceparent` response header; `TracingModule` flushes spans on shutdown. Add spans with `trace.getTracer('<module>').startActiveSpan(...)` from `@opentelemetry/api` (no-op when tracing is off); like metric labels, never put secrets or personal data into span attributes.
- `deploy/observability` depends on these metric names: the alert rules in `prometheus/rules/api.yml` (promtool tests in `prometheus/tests/`) and the Grafana dashboard `grafana/dashboards/api.json`. Update them in the same change when renaming a metric or label, when adding on-demand jobs to the `audit`/`maintenance` queues (`ScheduledJobMissed` assumes they only carry nightly scheduler jobs), or when adding a scheduler on another queue.

## Tests

- Unit specs sit next to the code (`*.spec.ts`) and must stay offline; mock `fetch` with `vi.stubGlobal`.
- E2E specs boot the real `AppModule` on Fastify with `configureApp` (same as production) against testcontainers Postgres/Redis/RustFS, a fake OpenAI-compatible embeddings server (`test/support/fake-embeddings.ts`; model `fake-<n>` returns n dims, `broken` returns 500) and a fake clamd (`test/support/fake-clamd.ts`, so every upload is scanned; files containing `FAKE_MALWARE` are infected, `FAKE_SCAN_ERROR` makes the scan fail). Mail is captured by overriding `MAIL_TRANSPORT`. Use helpers in `test/support/test-app.ts` (`createTestApp` (a second instance of a multi-instance test passes `{ mailbox: first.mailbox }`, since either worker may send queued mail), `registerUser` for client users (requests and reads the emailed code via `requestRegisterCode`), `loginAdmin`/`createAdmin` for admin accounts, `waitFor`). Files run serially and each starts with a flushed Redis; files that change runtime settings delete `system_settings` rows in `afterAll`; the e2e super admin is `E2E_ADMIN` (send only `email`/`password` when logging in: unknown body fields are a 400).
- Core logic changes (auth, rbac, rag, storage, config) need updated unit and/or e2e tests in the same change.

## Production notes

- Required: `NODE_ENV=production`, `JWT_SECRET` (≥32 chars), `ENCRYPTION_KEY` (32 bytes base64; rotate it via `ENCRYPTION_KEYS_PREVIOUS` + `node dist/scripts/reencrypt-secrets.js [--dry-run]`, steps in `deploy/README.md`), real `DATABASE_URL`/`REDIS_URL`/`STORAGE_*`/`SMTP_*`, `PUBLIC_URL`, `APP_WEB_URL`, `CORS_ORIGINS`; set `TRUST_PROXY=true` behind a proxy. Swagger is off and cookies are `Secure` by default in production.
- Deploy: `pnpm build` → `node dist/scripts/migrate.js` (`db:migrate:prod`) → `node --import ./dist/tracing.js dist/main.js` (`start:prod`). Seed once with `node dist/scripts/seed.js` and `SEED_ADMIN_*` (creates the first admin console account). The production image (`Dockerfile`, built from the repository root) runs all three; `deploy/` wires them up with Docker Compose (`deploy/README.md`).
- Migrations run in one transaction before the new release starts, and rollback redeploys the previous image without undoing them. Keep every migration compatible with the previous release's code (add nullable/defaulted columns; rename or drop in later releases), and never put non-transactional statements such as `CREATE INDEX CONCURRENTLY` in a migration. CI fails when the schema changed without `pnpm db:generate`.
- New runtime files outside `dist/` and `drizzle/` must be copied into the image explicitly in `Dockerfile`.
- Embedding base URLs are admin-controlled outbound requests; only grant `embedding-model:manage` to trusted administrators.
- Uploads are only malware-scanned with `CLAMAV_HOST` set (deploy profile `antivirus`, `deploy/README.md`); production logs a warning at boot without it.
- Tracing exports only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set and the process was started with the `--import ./dist/tracing.js` preload (the image's default `CMD`).
